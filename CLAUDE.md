# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm run dev` — Turbopack dev server. The script first deletes `public/sw.js` and `public/sw.js.map`, because Serwist only wraps the Next config in production (`next.config.ts`); a stale SW from a prior build will otherwise intercept requests in dev.
- `npm run build` — production build; this is the only path that generates the service worker via Serwist.
  **Never run it while `npm run dev` is up**: both write to `.next/`, and the build clobbers the dev server's manifests, which then 500s on every route until `.next` is deleted and dev is restarted. Verify with `npx tsc --noEmit` and `npm run lint` instead, or stop dev first.
- `npm run start` — serve the production build.
- `npm run lint` — ESLint (`eslint.config.mjs`, extends `next/core-web-vitals` + `next/typescript`).

There is no test runner configured.

## Environment

Copy `.env.local.example` → `.env.local`. Both a Firebase client config (`NEXT_PUBLIC_FIREBASE_*`) and Firebase Admin service account (`FIREBASE_PROJECT_ID`/`CLIENT_EMAIL`/`PRIVATE_KEY`) are required. The Admin credentials are used in two places: the edge middleware verifies the session cookie with them, and the Node-runtime API routes (`/api/gemini-token`, `/api/openai-live-session`, `/api/simli-token`, `/api/liveavatar-token`, `/api/session-active`, `/api/session-usage`, `/api/admin/usage` — all `export const runtime = 'nodejs'`) initialize `firebase-admin` through `src/lib/firebase/admin.ts` to read and write Firestore with rules bypassed. `COOKIE_SECRET_CURRENT`/`COOKIE_SECRET_PREVIOUS` sign the session cookie (two slots so secrets can be rotated). `GEMINI_API_KEY` is server-only, as is `OPENAI_API_KEY` (optional — only the GPT-Live voice model needs it), as are the optional avatar keys: `SIMLI_API_KEY` (plus `SIMLI_DEFAULT_FACE_ID`) and `LIVEAVATAR_API_KEY` (plus `LIVEAVATAR_DEFAULT_AVATAR_ID`).

`FIREBASE_PRIVATE_KEY` is stored with literal `\n` sequences and un-escaped at read time everywhere it's consumed (`middleware.ts` and the shared `authConfig()` in `src/lib/firebase/auth-config.ts`, which the Node API routes import).

## Architecture

Next.js 15 App Router + React 19 + Tailwind 4 + Firebase Auth/Firestore. The app lets users practice a foreign language by speaking with Gemini Live over a WebSocket.

### Auth: two halves that must agree

- **Client** (`src/lib/firebase/client.ts`, `src/providers/AuthProvider.tsx`, `src/hooks/useAuth.ts`) — Firebase Web SDK, `onAuthStateChanged` drives an `AuthContext`. `useAuth` exposes `login`/`logout` only; there is no client-side signup.
- **Edge** (`src/middleware.ts`) — `next-firebase-auth-edge` verifies a signed `AuthToken` cookie on every matched request. The matcher in `middleware.ts` is the authoritative list of protected routes (pages plus `/admin/:path*`, `/api/gemini-token`, `/api/openai-live-session`, `/api/simli-token`, `/api/liveavatar-token`, `/api/session-active`, `/api/session-usage`, `/api/admin/:path*`); adding a new authenticated route requires updating it. Authenticated users hitting `/login` or `/signup` are bounced to `/dashboard`; unauthenticated users hitting anything other than the public allow-list (`/`, `/login`, `/signup`, `/api/login`, `/api/logout`) are redirected to `/login`. `/` currently just redirects to `/login`; the marketing landing page is stashed at `src/components/landing/LandingPage.tsx` until launch.

Route groups reflect this split: `src/app/(auth)/` for login and the `/signup` invite-only notice (public signup is closed; the route stays so old links land somewhere), `src/app/(app)/` for authenticated pages (uses `AppLayout`).

### Access gate (invite-only)

Authentication isn't authorization: a Firebase Auth user can exist without being entitled to a session. Verba is **invite-only**: every valid token in `handleValidToken` is run through `isAccessAllowed` in `src/config/access.ts`, which passes only if the token carries an `admin: true` or `allowed: true` custom claim. The email domain grants nothing by itself; an account on your school domain without a claim is refused. Failures are redirected to `/login?reason=not-allowed` **and** have the `AuthToken` cookie deleted, so a disallowed account can't sit on a valid session; `LoginReasonBanner` then signs out the client SDK and says the account hasn't been invited. `firestore.rules` mirrors the same check as `isMember()`: conversations and usage reads need `isMember()` plus ownership, and scenario reads need `isMember()`. "Enable create (sign-up)" is also turned off in Firebase Console (Authentication › Settings › User actions), so the public API key can't create accounts; the Admin SDK still can.

There is no public signup. `/signup` renders a notice pointing invitees to `/login`. Invite people with `scripts/invite.mjs`:
- `node scripts/invite.mjs <email>` creates the Auth user with no password if needed, sets `allowed` (merged, so `admin` is kept), and prints a password-reset link. Send the link to the invitee; they set a password on Firebase's default action handler, then sign in at `/login`.
- `node scripts/invite.mjs <email> --password` does the same but sets a generated 16-character password (creating or overwriting) and prints it instead of a link, for handing someone their email + password directly. It's printed once and stored nowhere else.
- `node scripts/invite.mjs <email> revoke` removes `allowed` (never `admin`, never deletes the user) and calls `revokeRefreshTokens`, so existing sessions die at the next token refresh (within about 1h).
- `node scripts/invite.mjs <email> unlimited` sets the `unlimited` custom claim on an existing user (merged, so `admin` and `allowed` are kept); `... unlimited-off` removes it. `unlimited` skips the daily caps and the weekly practice budget but grants no access by itself (the account still needs `allowed`). It takes effect at the next ID token refresh (within about 1h, or at once after signing out and in).
- `node scripts/invite.mjs --list` is read-only and prints every Auth user's email, access (admin/allowed/none), limits (`standard`, `unlimited`, or `none` for admins) and last sign-in.

`scripts/set-allowed.mjs` still flips the `allowed` claim on an existing user; admins are set via `scripts/set-admin.mjs`. The scripts act on whichever Firebase project `.env.local` points at, so if dev and prod share one, invites and revokes are live.

### Gemini Live: ephemeral tokens only

`GEMINI_API_KEY` never reaches the browser. `src/app/api/gemini-token/route.ts` rejects any model not in `EPHEMERAL_TOKEN_MODELS` with a 400, and otherwise mints a short-lived token (1 use, 5 min) via `@google/genai` `authTokens.create` on `v1beta`. `src/lib/gemini/live-client.ts` speaks exactly one endpoint: `v1beta ...BidiGenerateContentConstrained?access_token=...`, with `realtimeInput.audio` payloads (`mediaChunks` is rejected on `v1beta` with close code `1007`).

Adding a **Gemini** model to `src/config/models.ts` therefore requires adding it to `EPHEMERAL_TOKEN_MODELS` too, and a Gemini model that can't do ephemeral tokens can't ship. (OpenAI-provider models bypass this route entirely — see the GPT-Live section below.)

The token is minted with `liveConnectConstraints` pinning the session setup, so a leaked token can't be reused with a different system instruction or with tools attached. This makes the client's setup message and the token's constraint two copies of the same object that **must match exactly** — so `src/lib/gemini/build-live-config.ts` builds both, server-side, and the route returns the setup config alongside the token for the client to send verbatim. Don't reconstruct the setup in the browser; drift shows up as an opaque socket close, not a useful error. Note `buildLiveConfig` (raw-socket shape, nests `generationConfig`) and `buildTokenConstraintConfig` (SDK `LiveConnectConfig` shape, flattens it) are deliberately different shapes for the same session.

### Audio + session orchestration

`src/hooks/useLiveSession.ts` is the single place that wires the pieces together: it fetches a token, constructs a `LiveClient` with callbacks, then starts an `AudioRecorder` (`src/lib/gemini/audio-recorder.ts`, 16 kHz PCM → base64 → `sendAudio`) and an `AudioPlayer` (`src/lib/gemini/audio-player.ts`, queues and plays `inlineData` frames). `onInterrupted` clears the player queue. Transcript entries are appended from `inputTranscription` (user) and `outputTranscription` (AI) server events.

The system prompt fed to the session comes from `buildSystemPrompt(scenario, difficulty, languageName)` in `src/config/scenarios.ts`, which substitutes `{{LANGUAGE}}` into per-difficulty templates. Difficulty levels and language metadata (`src/config/languages.ts`) are the product's tunable content.

### GPT-Live (OpenAI) voice provider

A second voice provider behind the same "Voice model" dropdown. `src/config/models.ts` now tags every `LiveModel` with `provider: 'gemini' | 'openai'`; `useLiveSession` branches on `getLiveModel(model)?.provider` and nothing else in the app has to know which vendor is live.

**Flow.** The browser builds the whole WebRTC offer itself (`src/lib/openai/live-webrtc-client.ts`, `LiveWebRtcClient`): `getUserMedia` → `new RTCPeerConnection()` → add the mic track → create the `"oai-events"` data channel **before** `createOffer()` → `setLocalDescription` → wait for `iceGatheringState === 'complete'` (10 s cap) → POST the SDP to `/api/openai-live-session` → `setRemoteDescription({ type: 'answer', sdp })`. **The HTTP request is what starts the session** — there is no `session.start` client event for WebRTC — and the client only reports `connected` once a `session.started` data-channel event arrives (30 s timeout).

**Route.** `src/app/api/openai-live-session/route.ts` (`runtime = 'nodejs'`, in the middleware matcher) authenticates like `/api/gemini-token`, validates the SDP/system prompt/voice/backend model, then applies the same `reserveTokenIssuance` daily caps and weekly budget (skipped for admins and `unlimited` accounts, 429 with the same `reason` values), and calls `client.live.create({ session, transport })` from the `openai` npm SDK (v7.15.0 ships `live.create`). It returns `{ sessionId, sdp, reservationId, reservedSeconds }` (the last two are the weekly-budget reservation, null for exempt accounts) and never lets `OPENAI_API_KEY` near the browser. `audio.format` is deliberately **not** sent — WebRTC negotiates the media format through SDP and the API rejects an explicit format for that transport.

**Prompt split.** `src/lib/openai/live-prompts.ts` splits one scenario prompt into two. `backendInstructions` is the existing `buildSystemPrompt()` output (the pedagogy) behind OpenAI's recommended "voice conversation context" preamble, and goes to the delegated Responses model (`gpt-5.6-luna` by default, `gpt-5.6-terra` the alternative, `reasoning.effort: 'low'`). `voiceInstructions` is the frontend prompt: it **also carries the full scenario prompt** under "Scene and your role" (the voice model speaks every line, including the opener, so without the scene it plays a generic tutor and never opens as the barista/waiter), plus the speech rules (target language only, one or two sentences, match the pace, wait after each reply) and the delegation rules (corrections, explanations and vocabulary/grammar answers go to the backend). Because the model otherwise waits for the student to speak first, the client sends one `session.instructions.append` right after `session.started` (`buildGreetingInstruction`) asking it to open the scene in character with one line ending in a question.

**No turn-complete event.** GPT-Live emits `session.input_transcript.delta` / `session.output_transcript.delta` fragments (append in delivery order) but nothing that marks end of turn. End-of-turn is therefore derived in the browser: the remote audio is tapped through `/audio-worklet-processor.js`, each Float32 frame's RMS is compared against a small threshold, and the turn is considered over after 600 ms below it. That falling edge is what calls `handleTurnComplete()` (which in turn flushes `avatar.endUtterance()`). Interruption needs no client event — GPT-Live is full duplex and handles it itself.

**Audio graph.** The remote track is attached to a hidden **muted** `<audio>` element (Chrome will not deliver a remote WebRTC track into Web Audio otherwise) while a parallel `AudioContext({ sampleRate: 24000 })` does the real work: `createMediaStreamSource` → analyser → gain → destination, plus a worklet tap that converts to Int16 and pushes to the same `AudioSink` the Gemini `AudioPlayer` feeds. So `setMuted`/`setSink` on `LiveWebRtcClient` stand in for the `AudioPlayer` methods and **both avatar vendors work unchanged**.

**Usage.** Two things bill. (1) Wall-clock Live audio: `session.usage.updated` carries a cumulative `usage.seconds` snapshot (replace, never sum), and `session.closed` carries the final one — which is why `disconnect()` sends `session.close` and waits up to 15 s for `session.closed` before tearing down. `OPENAI_LIVE_USD_PER_MINUTE = 0.05`; `liveSeconds` is capped at 4 hours server-side. (2) The delegated Responses model's tokens: each backend response ends in a `response.event` envelope whose nested `event` is a Responses `response.completed` (also `.incomplete` / `.failed`), with usage at `event.response.usage` (`input_tokens`, `input_tokens_details.cached_tokens` / `.cache_write_tokens`, `output_tokens` — `ResponseUsage` in the `openai` SDK). Each response is its own usage record, so `LiveWebRtcClient` **sums** them, deduped by `event.response.id`. Cached and cache-write counts are subsets of input; reasoning tokens are inside output. `SessionTokenTotals` carries all of it as optional `liveSeconds`, `backendInputTokens`, `backendCachedInputTokens`, `backendCacheWriteTokens`, `backendOutputTokens`, `backendModel` and `provider`; the backend is priced per model from `OPENAI_BACKEND_RATES` in `src/config/pricing.ts` (a `null` or unknown model contributes $0 but its tokens are still stored). `disconnect()` resolves with the final `LiveUsageSnapshot` (or the last known one if `session.closed` times out) and never rejects. Creating a WebRTC session bills **15 s of initialization**, credited back once the session actually runs — so abandoned connects are not free, which is why the route is behind the daily caps.

**Ending a session.** The hook's `stop()` tears down synchronously and returns `{ usage: Promise<SessionTokenTotals> }`. Gemini's resolves immediately with the cumulative snapshot; GPT-Live's resolves when that session's `disconnect()` finishes (≤ 15 s). `stop()` detaches the client at once — it sets state to `disconnected`, mutes the partner and releases the mic — and every callback of a detached client is a no-op, so a new session started while the old usage is pending can't receive its transcript, state or numbers. The usage promise is bound to that client instance, never to shared refs.

Env: `OPENAI_API_KEY`, server-only. Without it the route 500s with `{ error: 'GPT-Live not configured' }` and the Gemini models are unaffected.

### Avatar (optional, two vendors)

Off by default; the session page's "Video partner" toggle turns it on, and a vendor `<select>` plus a face `<select>` pick which partner. All three persist in `localStorage` under `verba.avatar` as `{ on, vendor, faceId }` (the old `{ on, faceId }` shape migrates to `vendor: 'simli'`, and a faceId that doesn't belong to the resolved vendor is dropped).

**The vendor interface.** `src/lib/avatar/types.ts` defines `AvatarVendor`, `AvatarState`, `AvatarCallbacks` and `AvatarProvider` — media elements the provider owns, `start(sessionToken)`, `pushPcm24k`, `endUtterance`, `interrupt`, `stop`, `getState`. `src/lib/avatar/index.ts` exposes `createAvatarProvider(vendor, callbacks)` and `tokenEndpointFor(vendor)`; `useLiveSession` talks only to those, so it holds no vendor branches. Providers are deliberately React-free and load their heavy SDK through a dynamic `import()` inside `start()`.

The flow is a tap on the audio that already exists rather than a second model: `AudioPlayer.addData` pushes each decoded PCM16 chunk (24 kHz, mono) to an optional `AudioSink` before playing it, and the hook wires that sink to `provider.pushPcm24k`. Both vendors return the rendered face *and* the voice, so `AudioPlayer.setMuted(true)` silences local playback — the gain node sits after the analyser, so the visualizer keeps working either way. `onInterrupted` calls `provider.interrupt()` alongside `clearQueue()`, and `onTurnComplete` calls `provider.endUtterance()` off the ref (so `handleTurnComplete` stays a stable `useCallback`).

**Simli** (`src/lib/avatar/simli-avatar.ts`) — `pushPcm24k` **resamples 24 kHz → 16 kHz** (linear, carrying the fractional read position and last sample across chunks so boundaries don't click) and hands it to `sendAudioData`. `endUtterance()` is a no-op: Simli's `handleSilence` detects end-of-speech from the stream itself. `simli-client` is loaded from the `simli-client/dist/client` subpath — the package's own `dist/index.js` requires `./Client` while the file is `client.js`, which breaks on a case-sensitive filesystem. Renders a square 512×512 frame.

**LiveAvatar / HeyGen, LITE mode** (`src/lib/avatar/liveavatar-avatar.ts`) — `start()` POSTs `api.liveavatar.com/v1/sessions/start` with the session token as a bearer, joins the returned LiveKit room with `livekit-client` (explicit dependency, deduped with the copy `simli-client` pulls), attaches the remote `heygen` participant's video/audio tracks to our elements, and opens the returned `ws_url`. Audio is a **24 kHz passthrough — no resampling** — batched into ~250 ms chunks (6000 samples) and sent base64 as `agent.speak`; `endUtterance()` flushes the remainder then sends `agent.speak_end` + `agent.start_listening`, and the first chunk of a turn is preceded by `agent.stop_listening`. `interrupt()` drops the buffer and sends `agent.interrupt`. A `session.keep_alive` goes out every 60 s. `start()` resolves only once the websocket reports `session.state_updated: connected` **and** the video track has attached, with a 15 s overall timeout. Inbound `error` frames with code `video_starvation` are logged as warnings and never tear the session down. Renders 16:9.

**Token routes.** Neither API key reaches the browser. `src/app/api/simli-token/route.ts` validates `faceId` against `AVATAR_FACES.simli` (or `SIMLI_DEFAULT_FACE_ID`) and mints from `api.simli.ai/compose/token`. `src/app/api/liveavatar-token/route.ts` validates `avatarId` against `AVATAR_FACES.liveavatar` (or `LIVEAVATAR_DEFAULT_AVATAR_ID`) and mints from `api.liveavatar.com/v1/sessions/token` with the `X-API-KEY` header, returning `{ sessionToken, sessionId }`; its `GET` returns `{ defaultAvatarId }`. Both are `runtime = 'nodejs'`, are in the middleware matcher, and deliberately do **not** check the daily caps — `/api/gemini-token` already gates the session.

Env: `SIMLI_API_KEY` / `SIMLI_DEFAULT_FACE_ID`, `LIVEAVATAR_API_KEY` / `LIVEAVATAR_DEFAULT_AVATAR_ID`, all optional and server-only. **LiveAvatar's free tier is 10 minutes/month** with a 5-minute idle timeout, and sessions die when credits run out — which is why `stop()` awaits `room.disconnect()`, a failed `start()` tears its own session down, and the hook's unmount cleanup matters more here than for Simli.

Every failure path degrades to audio-only rather than failing the session: the token fetch runs in parallel with the Gemini one and resolves to null on error, and if the avatar errors or stops mid-session `useLiveSession` drops the sink, unmutes the player, and shows a short `avatarError`.

### Scenarios: Firestore-backed, module fallback

Scenario content lives in the **top-level `scenarios/{id}` collection**, read through `src/lib/scenarios/store.ts` (`fetchAllScenarios` ordered by the `order` field, skipping docs with `archived: true` unless `includeArchived`; `fetchScenario` returns archived docs too, because history has to resolve titles for retired scenarios). The `scenarios` array in `src/config/scenarios.ts` is **only a fallback** — `fallbackList()` is used when the collection is empty, returns no valid docs, or the read throws. Editing that module does not change what users see in a seeded environment. `buildSystemPrompt` still lives in `scenarios.ts` and is still the live prompt builder.

Seed or re-seed the collection with `scripts/seed-scenarios.mjs`. Day-to-day editing happens in the admin UI at `/admin/scenarios`, which writes with the **client** Firebase SDK — so `firestore.rules` is the actual authorization boundary there (`scenarios/{id}`: read for any member (`isMember()`: `admin` or `allowed` claim), write only with `request.auth.token.admin == true`), not any server check.

### Data model

Firestore, with `src/config/firestore.ts` helpers; `firestore.rules` and `firestore.indexes.json` live at the project root.

- `users/{uid}/conversations/{id}` — saved transcripts, owner-only read/write, and the owner must be a member (`isMember()`).
- `users/{uid}/weeks/{weekStartKey}` — the weekly practice budget (see "Weekly practice budget" below). Owner-readable, member only, **write-denied by rules**; all writes go through the Admin SDK.
- `users/{uid}/usage/{dateKey}` — per-day counters and cost totals. `dateKey` is a Pacific-time `YYYY-MM-DD` string (`Intl.DateTimeFormat('en-CA', { timeZone: 'America/Los_Angeles' })` in `src/lib/usage.ts`), so "today" rolls over on campus time regardless of server or client zone. Owner-readable, member only (the UI shows sessions remaining), **write-denied by rules** — all writes go through the Admin SDK.
- `scenarios/{id}` — scenario content; readable by any member, writable only by admins.

### Daily session cap

Two counters in the same `users/{uid}/usage/{dateKey}` doc, because neither alone works: token issuances are cheap to force and don't imply a real session, while real sessions can only be confirmed after the fact.

- `tokenIssuances` — incremented inside a Firestore transaction by `reserveTokenIssuance()` every time `/api/gemini-token` mints a token. Cap `DAILY_TOKEN_ISSUANCE_LIMIT = 30`; exceeding it is a 429 with `reason: 'rate-limit'`. This bounds retries and abandoned connects.
- `realSessions` — incremented by `recordRealSession()` when the client POSTs `/api/session-active` **10 seconds into recording** (`useLiveSession.ts`; the code calls it a "beacon" but it is a plain fire-and-forget `fetch`, not `sendBeacon` — a failure just means the counter doesn't tick). Cap `DAILY_REAL_SESSION_LIMIT = 10`; exceeding it is a 429 with `reason: 'daily-limit'`.

Both limits are in `src/config/limits.ts`. `reserveTokenIssuance` checks the weekly budget first, then `realSessions`, then `tokenIssuances`, so the user-facing message is the longest-lived limit that applies ("resets Monday" beats "come back tomorrow", and the daily cap beats the anti-abuse cap). A refused start increments nothing. Callers holding the `admin` custom claim (`scripts/set-admin.mjs`) or the `unlimited` claim (`scripts/invite.mjs <email> unlimited`) skip every check, daily and weekly (`isLimitExempt()` in `src/lib/usage.ts`, used by both start routes and `/api/session-active`) — which is why their counters never move.

**Per-session limits.** The daily caps bound how many sessions start, not how long one runs, and GPT-Live bills wall-clock connected time — so a forgotten tab would otherwise cost money until closed. `src/config/limits.ts` also holds `SESSION_MAX_SECONDS` (20 min, warning at 2 min left) and `SESSION_IDLE_TIMEOUT_SECONDS` (3 min without student speech, "still there?" warning with an "I'm still here" button 30 s before). These are **client-side only** (nothing on the server enforces them), apply to both providers, and live in `src/hooks/useSessionLimits.ts`: the hard limit is `min(SESSION_MAX_SECONDS, reservedSeconds)` (the weekly-budget reservation, passed in as `maxSeconds`) and reads the page's connected-only `elapsed` counter; speech is detected by sampling the `userAnalyser` mic node every 250 ms (RMS > 0.02 on two consecutive samples), with growing `role: 'user'` transcript text as a secondary signal. Auto-end goes through the session page's `handleStop()` via `handleStopRef` (never the hook's bare `stop()`), so usage is still POSTed and the transcript still saved; `endingRef` makes `handleStop` run once even if End is clicked as a limit fires. Afterwards the page shows a neutral notice explaining why the session ended, cleared on the next start. Because a GPT-Live save can land up to ~15 s after End, `sessionGenRef` (bumped on every start) drops a notice whose session the student has already moved past.

**`handleStop()` flow.** `endingRef` guard → `stop()` (the page is idle and a new session can start immediately; it also settles the weekly reservation, see below) → capture this render's transcript and scenario metadata → `await usage` → if `hasUsage(tokens)`, fire-and-forget POST to `/api/session-usage` → save the transcript with those same `tokens` → resolve `true` if a transcript was saved. The unmount cleanup in `useLiveSession` calls `stop()` and ignores the promise; usage there was never saved.

### Weekly practice budget

Every student gets `WEEKLY_PRACTICE_SECONDS` (30 min) of connected practice per week, server-enforced, on top of the daily caps and the per-session limits. It exists for cost: GPT-Live bills $0.05 per connected minute and nothing else bounds total connected time (10 sessions × 20 min is 200 min a day). Constants are in `src/config/limits.ts`; admins and `unlimited` accounts skip it.

**Where it lives.** `users/{uid}/weeks/{weekStartKey}`, where `weekStartKey` is the Monday (Pacific time, same zone as the daily `dateKey`) as `YYYY-MM-DD`; weeks run Monday 00:00 to Sunday 23:59 Pacific. Fields: `weekStart`, `usedSeconds` (sum of settled charges), `updatedAt`, and `reservations: { [rid]: { seconds, createdAtMs, confirmed, settled, chargedSeconds, settledAtMs? } }`. The map is bounded by the daily issuance cap (≤ 210 entries a week). The accounting is pure and shared: `src/lib/weekly-budget.ts` (`reservationCharge`, `weeklyRemainingSeconds`, `weekStartKey`, reservation id helpers) is used by the server inside transactions and by the client (`useWeeklyBudget`), so both compute "remaining" the same way.

**Why reserve-and-refund.** The browser is the only thing that knows how long a session ran, and a closed tab reports nothing. So time is charged pessimistically up front and refunded when the client reports.

**Lifecycle.**
1. **Reserve** — `reserveTokenIssuance()` (both start routes) reads the day and week docs in one transaction. Remaining under `WEEKLY_MIN_START_SECONDS` (60 s) → 429 `reason: 'weekly-limit'`. Otherwise it reserves `min(SESSION_MAX_SECONDS, remaining)` under a random `rid` and returns `reservationId` (`{weekStartKey}_{rid}`, so a session that crosses midnight Sunday settles in the week it was reserved in) and `reservedSeconds` in the route's JSON. The routes reserve **after** request validation, and release the reservation themselves if the vendor call then fails.
2. **Confirm** — the 10-second `/api/session-active` ping carries `reservationId` and sets `confirmed: true` (alongside the daily `realSessions` count).
3. **Settle** — `/api/session-usage` with `{ reservationId, connectedSeconds }` charges `min(connectedSeconds, seconds)` into `usedSeconds` and marks the reservation `settled`; the rest is released. Settling twice is a no-op. `connectedSeconds` is measured in `useLiveSession` from the provider's own `connected` state (both providers), sanitized and capped like the other usage fields. The hook sends the settle as **its own POST**, `keepalive`, from `stop()` (so End, auto-end and unmount all settle, and GPT-Live's ≤ 15 s usage wait doesn't hold the time) and also when a session ends by itself (socket closed, connect failed, network drop) or a reservation lands after the session was already stopped. The token-usage POST from `handleStop` is unchanged.
4. **Lazy rules** (applied wherever remaining is computed, no cron): settled → its `chargedSeconds`; confirmed but unsettled → the full reservation; unconfirmed and older than `RESERVATION_CONFIRM_WINDOW_SECONDS` (2 min) → 0 (the connect failed); unconfirmed and younger → the full reservation (still connecting). A settle after a lazy release still charges.

**Trade-offs, accepted.** A closed tab (or a crashed browser) on a confirmed session costs the **whole reservation**, up to 20 min, because nothing reports. In-app navigation does not: unmount settles through `keepalive`. The client's numbers are trusted: a modified client can under-report `connectedSeconds` or skip the confirm ping (its reservation is then released after 2 min), so the budget stops honest overuse and forgotten tabs, not a determined cheater; the daily `tokenIssuances` cap still bounds that case.

**Client.** The session's hard cap is `min(SESSION_MAX_SECONDS, reservedSeconds)`; when the budget is what ended it, the end notice says the week's time is used and resets Monday, and the time warning says "left of this week's practice time". The idle screen warns when under 5 min is left (`WEEKLY_LOW_WARNING_SECONDS`). `SessionsRemaining` on the dashboard shows weekly minutes left as the primary line (30-segment minute meter) and today's sessions as a secondary line; admins and `unlimited` accounts see "No practice limit."

### Cost tracking

The Gemini Live API reports `usageMetadata` as **cumulative per-session totals** on each event, so `useLiveSession` overwrites rather than sums; GPT-Live usage is described in its section above. `stop()` returns `{ usage }`, a promise of the session's final `SessionTokenTotals`, and the session page POSTs it to `/api/session-usage` once it resolves. The route sanitizes and caps each field (the numbers come from the browser; backend cached/cache-write counts are capped at the input count, and `backendModel` must be in `OPENAI_BACKEND_MODELS`). Rates live in `src/config/pricing.ts`, each dated and sourced in a comment — update `PRICING_VERIFIED_DATE` when you touch them. `estimateCostBreakdown()` splits a session's cost by what produced it (Gemini token fields → Gemini; `liveSeconds` + backend tokens → OpenAI), not by the `provider` tag; `estimateCostUsd()` is its total.

`recordSessionUsage()` increments, all with `FieldValue.increment` in `users/{uid}/usage/{dateKey}`: the Gemini token fields, `liveSeconds`, `backendInputTokens` / `backendCachedInputTokens` / `backendCacheWriteTokens` / `backendOutputTokens`, `estimatedCostUsd` (the **total**, kept so old readers still work), `geminiCostUsd`, `openaiCostUsd`, `openaiBackendCostUsd` (subset of `openaiCostUsd`), and `geminiUsageSessions` or `openaiUsageSessions` (sessions that POSTed usage — distinct from the cap's `realSessions`). Docs written before the split have only `estimatedCostUsd`, so readers show `estimatedCostUsd − geminiCostUsd − openaiCostUsd` (clamped ≥ 0, per doc) as "Unattributed (before split)" rather than guessing a provider.

`/admin/usage` reads aggregates from `/api/admin/usage`, which checks the `admin` claim server-side and sweeps `collectionGroup('usage')` with the Admin SDK. The page shows per-provider cost tiles (Gemini, GPT-Live with minutes and backend cost, and Unattributed when non-zero), per-user provider columns, and daily bars stacked by provider (Gemini `brand`, GPT-Live `accent` fill — never as text — and unattributed `rule` grey) with a legend.

### Admin pages

`/admin/scenarios` (list + `[id]` editor) and `/admin/usage` (cost dashboard) share the `AdminTabs` sub-nav (`src/components/admin/AdminTabs.tsx`); the header's Admin link points at `/admin/scenarios`. Both pages gate client-side on `getIdTokenResult().claims.admin` and `router.replace('/dashboard')` otherwise — that's UX, not security. The real enforcement is `firestore.rules` for scenario writes and the claim check in `/api/admin/usage` for usage data. `/admin/:path*` and `/api/admin/:path*` are in the middleware matcher, so unauthenticated access never reaches them.

### PWA / Service worker

`@serwist/next` wraps the Next config **only in production** (`next.config.ts`); dev uses plain Turbopack. `src/app/sw.ts` forces `NetworkOnly` for `firestore|firebase|identitytoolkit|securetoken|googleapis|generativelanguage` hosts so auth and Gemini traffic never hit the cache, and provides `/~offline` as the document fallback. `src/app/manifest.ts` declares the PWA manifest.
